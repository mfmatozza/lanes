# Multiplayer scale test, 2 November 2026

Status: **engineering measurement**, not a benchmark of agent behaviour. No LLM is involved: a script sends the hook events real agents would send. Nothing here goes on the site or in a deck. (#261)

## Setup
- **Script:** [`scripts/e2e/scale.mjs`](../../scripts/e2e/scale.mjs). Deterministic (seeded), everything in a temp folder, `LANES_HOME` temp, `LANES_AUTOSTART=0`.
- **Lanes:** branch `feat/mp-scale`, from `7f801a9` on `feat/multiplayer-shared-context`.
  - "Before": `7f801a9`.
  - "After": the three fixes below.
- **Machine:** Windows 10, 16 logical CPUs, 32 GB RAM, Node 24.20.0. The server, every hook process, git and the load generator share this one machine, so hook latencies include CPU contention from the load itself.
- **Server:** the bundled `dist/server.cjs` on loopback, with a request log (`LANES_LOG`) for server-side latency. One extra run used the source build (`--source`: `packages/server/src/main.ts`, `packages/hook/src/hook.ts`).
- **Teammates:** K = N/4 (at least 2).
  - Each has its own `LANES_HOME`.
  - Each has a personal token: `POST /v1/members/invite` on the server's machine, then `lanes join` on the teammate's side.
  - Each has a clone of each of the 2 bare origins, set up with `lanes init --agents claude,codex,gemini,cursor`.
  - Team context is on (`.lanes/team.json`).
- **Agents:** N agents spread round-robin over teammates, repositories and the four event shapes. Each is invoked as the installed hooks are (`hook.cjs <event> --lanes [gemini|cursor]`):
  - **Claude:** Edit/Write with `old_string`.
  - **Codex:** `apply_patch`.
  - **Gemini:** `replace`/`write_file`.
  - **Cursor:** `conversation_id`, `afterFileEdit` only, no pre hook.
- **Agent loop:**
  - start, then turns of: prompt, 4 edits (pre, write, post), stop. Then end.
  - The edits alternate between a one-line append to a hot file (`src/hot0.ts` 70 %, `src/hot1.ts` 30 %) and a rewrite of one of 6 cold files per agent.
  - Think time between edits is 1.5–4.5 s, much busier than a real agent.
  - An agent told "that edit is not in the file now" re-applies it (up to 3 times), as the soak does. Cursor cannot be told.
- **Team:**
  - Every 5–15 s each teammate posts a chat message with an @mention (20 % `@team`).
  - With 40 % chance it also asks a random teammate something (read scope).
  - It approves the pending requests addressed to it.
- **Viewers:**
  - V WebSocket clients: half browser app (token in the query, Origin header), half VS Code (a teammate's token in the header).
  - A refused viewer falls back to `GET /v1/state` every 5 s, as both clients do.
  - 2 more pollers, plus a sampler (server RSS via `tasklist` and snapshot size every 5 s).
- **Run length:** 1.5 minutes of load per run, plus setup and drain. Every run is listed below.

## What is checked
- **Hook latency:** p50, p95 and p99 per event, from spawn to exit.
- **Server-side latency:** per route, from the server log.
- **Server RSS over time.**
- **Snapshot size:** bytes, and bytes per top-level field at the end.
- **Stream traffic:** WebSocket bytes and frames per second per client.
- **Brief size:** the brief (`team-context` without path) and the heads-up, as served.
- **Lost lines:** a hot-file line missing from `lanes/main`, and missing from the author's clone too.
- **Unpublished:** missing from `lanes/main` but still committed in the clone.
- **Cold files:** the last content written must be on `lanes/main`.
- **Refusals:** any hook output with a permission decision, `deny`, `continue: false`, or `block` outside Stop. Must be 0.
- **Other:** hook exit codes, fail-open messages, conflict markers and duplicated lines on `lanes/main`.

## What broke, and what was fixed

### 1. Edits undone by another agent in the same checkout (data loss)
**Symptoms**
- A codex agent's cold-file rewrite (N=8) and a cursor agent's appended line (N=16) were in no commit.
- Conflict markers reached `lanes/main` (N=16).

**Cause**
- An agent writes its file after its pre hook returns and before its post hook runs, outside any lock.
- Meanwhile another session's publish in the same checkout runs `rebase --autostash`, or `stash push` / `reset --hard` / `stash pop` (moveOntoShared).
- A write that lands inside that window is reset away, or ends up in a conflicted `stash pop` that writes markers into the file.

**Fix**
- The pre hook marks the edit as in flight (a file under `LANES_HOME/inflight/<checkout>`). It does so under the checkout lock, so any git operation already running finishes first.
- The post hook clears the mark, and so do the stop and end hooks. A PermissionRequest hook refreshes it. Marks expire after 10 minutes.
- While another session's edit is marked, `rebaseOnto` treats the checkout like one with the human's overlapping uncommitted work: no sync into the working tree, and the publish goes out as a replayed tip in memory.
- A session's own mark never blocks its own git operations.
- Cursor has no pre hook, so its whole turn (prompt to stop) is marked.

**Tests**
- `packages/hook/test/inflight.test.ts`.
- A hook test that left a pre without a post now ends its session.

### 2. One snapshot serialised per viewer per change
**Cause**
- Each stream built and stringified its own snapshot on its own 50 ms timer.
- With 60 viewers that was 60 builds per change.

**Fix**
- One debounced broadcast builds the frame once and writes it to every stream.

**Test**
- `events-ws.test.ts`: 5 viewers, 1 change, 1 build.

### 3. Snapshot size growing with every prompt
**Cause**
- Every task up to 1,000, finished ones included, went to every viewer on every change.
- In these runs, tasks are the largest part of the snapshot (about 340 B per task).

**Fix**
- `GET /v1/state` and the stream carry every active task and each person's latest 10 finished ones. The VS Code board shows 3.
- Team context still reads the full list.

**Test**
- `packages/server/test/scale.test.ts`.

**Effect**
- The 1.5-minute runs never reach the 10-per-person bound, so the table does not show it.
- At 1,000 tasks the old snapshot would have been about 340 KB, times about 4 frames/s, times every viewer.

### 4. MAX_STREAMS 50
**Symptom**
- 60 viewers meant 10 refused, falling back to polling.

**Fix**
- Raised to 128: a team of 30 with the app and two VS Code windows each is 90.
- The slow-reader backlog was lowered from 4 MB to 2 MB, so the worst case stays at 256 MB if every client stops reading.

**Tests**
- The 129th connection is refused (`events-ws.test.ts`, `ws-probe.mjs`).
- `protocol.md` and `security.md` are updated.

### 5. Ended session ids kept forever
**Cause**
- `Coordinator.endedSessions` grew by one per session, for the life of the server.

**Fix**
- Bounded to the latest 10,000.

**Test**
- `scale.test.ts`.

## Remaining limits (measured, not fixed)
- **Hot-file throughput.** A lease is held from pre until the publish in post has pushed.
  - With 2 hot files and an edit every few seconds per agent, the queue grows with N.
  - After the fixes, acquire waits reach p99 33–44 s at N=32 and about 100 s at N=64. The hook's wait cap is 240 s, then the edit goes ahead.
  - Real agents edit far less often than this script. The number that matters is edits per second per hot file, and publish time on a loaded machine (post p50 is 1.2 s at N=8 and 5–10 s at N=64).
- **Push contention at N=64.** Every publish is a compare-and-swap push to one origin.
  - 56–67 publishes per run exhausted their 8 attempts. Most were in Cursor sessions (45 of 58 and 48 of 51 in the first after runs).
  - A Cursor turn mark keeps the other sessions of that checkout on the slower replay path.
  - The work stays committed in the clone and goes out with the next publish there. A session that ends right after such a failure leaves it until someone publishes in that checkout again (7 edits in the N=64 V=60 run).
  - `shortcut:` not fixed. The options are a longer budget for the final publish, or a server-side publish queue.
- **Cursor gets no re-apply notice.**
  - When a Cursor edit overlaps newer content, the shared content wins and Cursor's version stays only in `refs/lanes/backup/*`. Cursor's afterFileEdit takes no context.
  - Seen once at N=64 (1 line).
  - Already listed as a shortcut in `hook.ts` (stop `followup_message`). Not implemented here because it is unverified against a real Cursor.
- **Request delivery falls with N:** 4–8 of 6–12 approved requests delivered at N=8–16, 0–16 of 20–44 at N=32–64.
  - An approved request reaches the receiver's agent only at its next prompt, in that repository, and not in a Cursor session.
  - At N=64 there are few prompts per agent in 1.5 minutes because turns wait on leases. Not investigated further.
- **The brief stays within its 2,000-character budget** (max 1,999), and the heads-up within 480. With more teammates the overview is shortened rather than the brief growing.
- **`editors` and file versions** grow with the number of distinct files ever published (bounded by the repository's size), and `editors` is in every snapshot.
- **A human's own uncommitted edits are not marked.** The window in which a Lanes git operation can race them is one git operation, as before.
- **The checkpoint trailer** says `Lanes-Agent: claude-code` for every agent kind (seen in Cursor commits). It is cosmetic and not changed here.
- **Flaky test:** `runtime.test.ts` "a state update survives a parallel hook reading the file all the time (#255)" failed in 2 of 3 full-suite runs on this machine (the third, final run passed: 337 pass, 0 fail, 2 skipped), always with EPERM after 100 rename retries under load. It passed alone each of 3 times, and this branch does not touch `saveState`.

## How to reproduce
```bash
npm run build
node scripts/e2e/scale.mjs --agents 16 --viewers 60 --repos 2 --minutes 1.5   # one run; prints the table rows and writes JSON
node scripts/e2e/scale.mjs --agents 16 --viewers 60 --repos 2 --source        # the same from packages/*/src/*.ts
```
- **Other flags:** `--teammates K` (default N/4), `--pollers P` (2), `--think ms` (3000), `--seed`.
- **Output:**
  - JSON results go to `$LANES_TMP` (or the OS temp folder) under `lanes-scale-results/`.
  - A failed run keeps its temp folder, with the server log and every clone. `SCALE_KEEP=1` keeps a passing one.
- **Safety:**
  - The script never touches `~/.lanes` or `~/.claude`: every `LANES_*` variable from the caller is dropped.
  - The server runs on a random port in 20000–39999 and is killed by PID tree (`taskkill /T /F`).
- **Windows only as written:** server RSS comes from `tasklist`, and the kill uses `taskkill`.
