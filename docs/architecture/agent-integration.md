## 1. Claude Code (MVP)

Lanes integrates through **Claude Code hooks** ([docs](https://code.claude.com/docs/en/hooks)). We don't fork, wrap or proxy the agent ([ADR-0005](../decisions/0005-claude-code-hooks-enforcement.md)).

### Hooks installed
**Set Up Repository** (or `lanes init`) merges these into `.claude/settings.json`, keeping existing hooks. That file is committed, so every teammate and every worktree gets them. Claude Code reads `.claude/settings.json` only from the folder it was started in (and sets `${CLAUDE_PROJECT_DIR}` to that folder), so for a monorepo, `lanes init` run from a subfolder (or `--dir packages/app`, or the extension's Set Up Repository in that folder) also writes `.claude/settings.json` there, pointing at the root's `.lanes/hook.cjs` through a relative path (#127). Claude started in a subfolder that was never set up runs no hooks: run init there, or start Claude at the repository root. Init also makes publishing work with no environment variable: with an `origin` it fetches `lanes/main` from it or creates it there from the remote default branch plus one setup commit holding only the Lanes files, never from the checked-out branch's unpushed commits (ADR-0021, #125) and the hook uses `origin` by default (`LANES_REMOTE` overrides it, `LANES_REMOTE=` forces local mode); without an `origin` it creates a local `lanes/main` and says that Lanes works on this machine only.

| Event | Matcher | Hook call | Purpose | On failure |
|---|---|---|---|---|
| `UserPromptSubmit` | — | `prompt` | Create the task from the prompt (title and predicted files only) | Continue |
| `SessionStart` | — | `start` | Register the agent; agent-only note about checkpoint commits | Continue |
| `PreToolUse` | `Edit\|Write\|MultiEdit\|NotebookEdit` | `pre` | **Acquire** the lease (waits in the queue), sync, re-read note | **Continue** (never blocks) |
| `PermissionRequest` | same | `permission` | Hold the lease while the user decides on the approval prompt | Continue |
| `PostToolUse` | same | `post` | Commit and **publish** the edit, release the lease | Continue |
| `Stop` | — | `stop` | Publish files changed during the turn (including shell-created ones), complete the task, mark idle | Continue |
| `SessionEnd` | — | `end` | Release leases; remove the agent | Continue |

```jsonc
// .claude/settings.json (excerpt)
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Edit|Write|MultiEdit|NotebookEdit",
      "hooks": [{
        "type": "command",
        "command": "node --no-warnings \"${CLAUDE_PROJECT_DIR}/.lanes/hook.cjs\" pre --lanes; exit 0",
        "timeout": 300, "statusMessage": "Lanes: coordinating with teammates…"
      }]
    }]
    // the other events: same shape, shorter timeouts
  }
}
```
The command is a shell line on purpose (#126): Claude Code starts an exec-form `command` + `args` hook without a shell, and a missing executable then shows a visible "hook error" on every event, whereas the shell line ends with exit 0 (no visible error) when `node` is missing, not on `PATH`, or an absolute path is stale. `; exit 0` (not `2>/dev/null || exit 0`, before Round 2) parses in bash, sh and Windows PowerShell alike, because Copilot also runs this file, through PowerShell on Windows, and refuses an edit on any non-zero exit (multiplayer research). It is the same on every OS, so the committed file never changes between machines. There is no `onFailure: "block"` anywhere ([ADR-0019](../decisions/0019-never-refuse-an-edit.md)). The `PreToolUse` timeout (300 s) is above the 240 s queue wait, so the hook, not Claude Code, ends a long wait.

**Why a `command` hook rather than an `http` hook?**
- Claude Code supports `http` hooks that POST straight to a URL. But the hook has to turn absolute file paths into **repository ID + repo-relative path**, and that needs local `git` and filesystem access.
- A command hook can also read per-user settings from `~/.lanes/config.json`, so the committed `settings.json` contains no personal data.

### Hook script behaviour (`.lanes/hook.cjs`)
- **Input:** the Claude Code hook JSON on stdin (`session_id`, `cwd`, `prompt`, `tool_name`, `tool_input.file_path` / `notebook_path`). Malformed input is treated as empty, which makes every event a no-op.
- **Configuration**, in order of precedence:
  1. environment variables `LANES_SERVER`, `LANES_USER`, `LANES_EMAIL`, `LANES_TOKEN`;
  2. `~/.lanes/config.json`;
  3. defaults: user = `git config user.name`, falling back to the OS user name.
  `lanes status` uses the same resolution (#129). The token is `LANES_TOKEN` or `config.json`'s `token`; without one, a server on this machine (loopback, or reached by one of this machine's own addresses or host names) uses `~/.lanes/token`, and a remote server gets no token and answers 401. `lanes connect --server <url> --token <t>` (or `lanes init --server <url> --token <t>`) writes `serverUrl` and `token` to `~/.lanes/config.json` (0600; a `--server` that is not an http(s) URL with a host, or a `--port` outside 1-65535, is refused with exit 2 before anything is written or started, #183); the extension's `lanes.serverUrl` / `lanes.token` settings are written to the same file, because hooks run outside VS Code (#123).
- **Bundle:** a single `.cjs` file with no dependencies. Repository identity is cached on disk and the hook uses `node:http`, not `fetch` (about 45 ms saved). p95 of `pre` is under 100 ms ([spike v3 report](../research/spike-v3-report.md); what exactly N1 measures is in [requirements](../product/requirements.md#4-non-functional-requirements), and `npm run bench` reproduces it). On Windows (Node 24, git 2.55, local origin, 300 files, 50 runs) the bundled hook measures: `pre` p50/p95 69/74 ms warm and 71/76 ms with a cold identity cache (0 git launches); `start` 181/246 ms; `post` with nothing to publish 131/137 ms; `post` for one edited file 598/641 ms (19 git launches, was 33 and 922 ms). How: the repository identity, the origin and the in-progress rebase/merge markers are read from the files in `.git` instead of `git` launches; the integration tip is asked with one `ls-remote` and fetched only when it moved; one `git log` replaces a rev-list, a show and a diff-tree per commit; the git identity is cached for five minutes; a file whose shared version is already in this checkout is not checked again; a `post` with nothing to commit and nothing unpublished returns before touching the network; automatic gc/maintenance is not launched behind Lanes' commits. **Publishing stays synchronous** in `post` (shortcut, #132): moving it into a background process would make the lease release and the "re-apply this edit" note arrive after the agent has already gone on, so a teammate could sync a tip that is not pushed yet and an overlapping edit could be overwritten before the agent is told; `stop` still publishes everything at the end of the turn either way. Revisit with a queue the next hook can drain.
- **`pre`:**
  - If the file isn't in a git repository, print nothing and exit 0.
  - Otherwise call `/v1/acquire` with `waitMs` up to 240 s. A local server that isn't running is **started automatically** first. `lanes server` on a port that is taken says so (#184): "already running at <url>" (exit 0) when a Lanes server with this token answers there, else "port N is already in use" (exit 1), and prints no token for a server that did not start.
  - **On allow:** sync the file from the integration branch if a newer version exists. If the file changed under the agent, print an **agent-only, neutral** "re-read this file" note. Print **no permission decision**, so the user's normal approval flow applies.
  - **On timeout, sync failure or an unreachable server:** exit 0 and let the edit go ahead. Nothing is printed. The views show "offline" or flag the problem.
- **`post`:** commit only the file the agent edited (with the repo's own hooks), fetch, rebase and push `lanes/main`, then call `/v1/publish`. If the remote is unreachable, the commit stays local. Only Lanes' own commits are pushed, never the human's earlier local commits ([ADR-0023](../decisions/0023-security-baseline.md)). Checkpoint commits are unsigned (`commit.gpgsign=false`): "signed" in [ADR-0017](../decisions/0017-edit-attribution.md) means authored as the human, because a failing or prompting signer inside a hook would otherwise block every publish.
- **Slow commit hooks and slow networks (bug hunt #81):** `post` has a 40 s timeout and `stop` 90 s. The repository's own commit hooks (husky, lint-staged, scanners) run inside `git commit`; the hook stops waiting for them after 12 s (30 s at `stop`) and sends the lease release anyway, leaving the commit running detached (never killed). Whatever lands later is published by the next publish, because every Lanes commit above the shared tip is sent. Fetches are cut off after 10 s and pushes after 20 s (`LANES_NET_TIMEOUT_MS` overrides both; `start` caps its own fetch at 2 s because its hook timeout is 5 s). The limits are generous on purpose: at 2 s, a loaded machine (CI) timed out healthy `ls-remote` calls and the remote was then treated as down (#141). A remote that could not be reached (timeout, DNS, refused; not a rejected push) is remembered per checkout in `~/.lanes/cache` with a growing pause (30 s, 60 s, 2 min, at most 5 min): hooks in that window skip the fetch and push altogether, so an offline laptop pays the timeout once, not on every edit, and `start` registers the session before it syncs (#131), and a publish stops retrying when less than one fetch of its budget (30 s, 70 s at `stop`) is left; the first attempt always runs. Each of these is reported to the views as `publish-commit-pending` or `publish-retries-exhausted`.
- **Parallel hooks (#83):** the hooks of one session may run at the same time. Session state is written atomically (temp file + rename, retried for up to 2 s when Windows refuses the rename because a parallel hook has the file open for an unlocked read, #255: before, the update and that edit's publish were lost) and updated under a per-session lock, and publishing and syncing (rebase, fetch into the tracking ref) are serialised per checkout by one lock (#143: a sync outside it collided with a publish on `index.lock`), with locks under `~/.lanes/locks` that fail open (a lock is abandoned after 90 s, and a wait that outlasts the hook's budget proceeds anyway).
- **The human's git state is never touched (bug hunt round 2: #100, #103, #108, #111):** while a rebase, merge, cherry-pick or revert is in progress, Lanes neither syncs nor commits (the publish reports a conflict and the edit is retried later) and never aborts an operation it did not start. A sync never rebases commits that are already on a remote: it merges the integration branch in instead (#124), so teammates' content still arrives and pushed history stays as it is; if the merge conflicts it is undone and the edit is published as a replayed tip. A human's uncommitted file that overlaps incoming content only skips the sync of the working tree: the agent's commits still publish through the same replayed tip (#128) and the hook reports `sync-skipped`. All name-only diffs use `--no-renames`, so a teammate's rename clashes with the human's uncommitted edit of the old name and a rename survives conflict recovery.
- **Publish robustness (bug hunt round 2: #106, #107, #109):** a Lanes commit that depends on the human's unshared commit stays local and is reported (`publish-blocked`); the independent commits after it still publish. Each checkpoint records a `Lanes-Files` fingerprint of the files it changed, so a commit the human amended or squashed content into is no longer treated as Lanes' and never travels. A `git add` that fails (path over 260 characters, `core.safecrlf`, a locked file) is retried per path, reported (`publish-add-failed`), and the file stays in the session's list until it is committed; Lanes' own git calls set `core.longpaths=true`.
- **Overlap on a branch with pushed commits (#144):** when a teammate's content overlaps the agent's unpublished edit and the branch holds commits that are already pushed (so history is never rewritten), the publish merges the shared tip with the shared content winning for the overlapping hunks (a new merge commit), keeps the agent's version in `refs/lanes/backup/<commit>`, replays the agent's commits onto the shared tip the same way, and tells the agent once to re-apply, exactly as in the unpushed case. Before, those commits stayed blocked for good and the agent was never told. Syncs without a publish never resolve a conflict this way.
- **A human's unpushed commits and a conflict with the shared tip (#244):** the rebase of an unpushed branch that carries a commit that is not Lanes' conflicts as soon as a teammate appended at the same spot (the normal "add a route" race), and the all-Lanes recovery (#240) rightly refuses to rewrite the human's commits, so the checkout used to publish nothing again. Now, when that recovery declines, the publish merges the shared tip into the branch (a merge commit, nothing rewritten, the human's commits and uncommitted files untouched). A file that conflicts only as two insertions at one spot is resolved keeping both sides' lines (the same resolution as #240, from the merge's three index stages); a file where both sides changed the same lines takes the shared content, the agent's version goes to `refs/lanes/backup/<commit>` and the agent is told once to re-apply (as in #144); a merge that still cannot complete is undone and reports `conflict`. The Lanes commits are then published as a replayed tip without the human's commits; the replay (`git merge-tree` per commit) applies the same insertion resolution, building the resolved tree in a temporary index, so a Lanes commit whose only conflict is an insertion at the shared spot is no longer reported as depending on the human's work. After the push, the branch is rebased onto the published tip when that is possible (the merge commit and the duplicates drop out); if not it stays merged, and the next publish recognises the replays it already pushed (`lanes-published`) instead of replaying or merging them again. Bounded work: a branch with more than 20 commits above the shared tip is synced by merging (a rebase that is going to conflict costs time per commit, at every sync), a publish replays at most 100 Lanes commits (`LANES_MAX_REPLAY`; the rest goes with the next publish) and tries the ones that did not apply last time (`lanes-blocked` in the git directory) after the new ones, so a few blocked commits never starve the rest or make every publish replay hundreds. Measured with `node scripts/e2e/soak.mjs --minutes 32` (4 agents, 2 clones, a human commit per minute, server restart, origin away): 0 of 1056 lines missing, `pre` p95 at most 3.7 s in every 5-minute window (about 23 s before), server RSS 112 to 120 MB, no latency growth over the run. shortcut: the human's branch keeps its own copies of what was published (about 950 commits ahead of the shared tip after the soak, 316 of them merges) and a `git pull --rebase` by the human replays them; Lanes never rewrites them. Revisit by dropping published Lanes commits from an unpushed branch.
- **Not a Lanes repository (#146):** a file inside a submodule or nested repository belongs to a repository that has an `origin` but no `lanes/main`. A publish there asks for the integration branch before its first commit (only when the tracking ref is not known), reports `publish-no-integration-branch` and leaves the edit uncommitted, so nothing is committed in the submodule and no unpushed submodule commit is published as a gitlink.
- **Stale locks and session files (#110, #114):** a lock records its owner's pid and is taken over at once when that process is gone (a lock of a live owner is waited for at most 20 s, `LANES_LOCK_WAIT_MS`, counted against the publish budget, so the lease release is always sent inside the hook's timeout). A lock is created with its owner already inside, released by renaming it aside (deleting in place when Windows refuses the rename because a waiter has the owner file open, #151) and taken over only through a gate that re-reads the owner (#141): before, a waiter could delete a live lock under load, two publishes ran in one checkout and a file stayed staged but never committed.. The `end` event deletes the session's state file unless files are still waiting to be published, and `start`/`end` delete state files older than 14 days.
- **`lanes init` when the setup commit fails (#186):** the files stay written and the command exits 1 with one line: git has no `user.name`/`user.email` (with the two commands to run), or the last `fatal:`/`error:` line git printed (line-ending warnings are dropped). Running `lanes init` again is safe.
- **`stop`:** publish files created or changed during the turn that the edit tools did not touch (not pre-existing dirty files, not secret-like names, at most 1 MB), then mark the task done.
- **File-system errors in the CLI (#187):** a folder or file the CLI cannot write (permission denied, read-only, disk full, or a file where a folder is needed, in the repository or in `~/.lanes`) is reported as one sentence naming the path and what to do, never as an `EPERM: ...` dump; a `--dir` that does not exist says so instead of "not a git repository".
- **`prompt`, `start`, `permission`, `end`:** best-effort calls that always exit 0.
- **Never printed to the agent:** teammates' names, "Lanes", queue state, overlaps or errors. Hook errors are redacted (URLs with credentials, absolute paths) before they are logged.
- **Requirements:** `lanes init` and `lanes pr` check for `git` first and say "git was not found on your PATH" instead of blaming the folder (#185). Node ≥ 20 (the committed hooks name a bare `node`. If `node` is not on `PATH` where `lanes init` runs, init writes the absolute path of the node that ran it into the user's own `.claude/settings.local.json`, adds that file to `.git/info/exclude`, and says so; the committed hooks stay silent on that machine, so nothing runs twice, and a later init with `node` on `PATH` removes the local entries; inside an editor that is not Node, init says to install Node, #113/#126), and `git` ≥ 2.38 for the full handoff (`merge-tree --write-tree`; re-applying overlapping edits on a branch with pushed commits needs ≥ 2.40 for `merge-tree -X`, below that they stay blocked and reported). On older git, commits that sit on top of a teammate's unshared human commits stay local and are reported instead of published.

### CLI conventions (installer audit)
- **Help and exit codes (#182):** `lanes`, `--help`, `-h` and `help [command]` print to stdout and exit 0, `lanes <command> --help` shows that command only. A wrong command line (unknown command, unknown option, missing value, stray argument) prints one line to stderr naming the problem and the `--help` to run, and exits **2**. A correct command that fails (not a repository, server offline, refused token) prints one actionable line and exits **1**; the CLI never prints a stack trace.

### Local ledger and `lanes report`
Lanes counts what coordination did for the edits on a machine, locally, so a team can see what its own downtime costs (pricing validation, ADR-0027). There is no telemetry: nothing leaves the machine unless the user sends it.
- **The ledger:** on each `pre` event the hook appends one line to `~/.lanes/ledger.jsonl`: `{ts, repo, kind, ms}`. `repo` is a short hash of the repository id, **never a name**; `kind` is `ok` (coordinated, no wait), `queued` (waited behind another agent, `ms` is the wait) or `failopen` (the server was down, unreachable or too slow, so the edit went ahead uncoordinated; a wait that ran out counts too). **No file paths, file contents, prompts, task titles or names, ever.** The file is capped (`LANES_LEDGER_MAX_BYTES`, default 256 KB): past the cap it is moved to `ledger.jsonl.1`, replacing the previous one, so it never holds more than about 512 KB. Writing is best effort and never fails an edit.
- **Reporting to the server:** a `failopen` entry also sets a flag. On the next successful contact the hook sends the server a count (`observe` with `kind: "uncoordinated"`, [protocol](protocol.md#uncoordinated-edits)) for that repository, once, and only for the last 7 days. The server keeps the sum per repository for a week in memory.
- **`lanes report [--json] [--file <path>] [--days <n>]`:** prints a copyable summary: edits seen, coordinated share (an estimate of server uptime), uncoordinated edits, weeks with at least one, collisions handled (queued), the 95th percentile queue wait, per repository (hash) numbers, and, if the server answers, how many people and agents it serves now (counts only). `--json` prints the same as JSON. `--file` writes a text file with the same summary and optional blank notes the user may fill in and email. It never contains paths, prompts, titles or names, and it sends nothing.
- **`lanes hosted`:** prints the email to join the waitlist for the hosted server (planned). A waitlist, not a purchase; nothing is sent from the command.

### `lanes pr`: one task, one clean branch (b.8)
`lanes pr [--task <id, session or part of the title>] [--branch <name>] [--base <branch>] [--no-gh]` tidies the many checkpoint commits of one task ([ADR-0022](../decisions/0022-checkpoint-commits-on-the-agent-branch.md)). It fetches `origin`, reads the commits `lanes/main` has and the default branch lacks, groups those that carry `Lanes-Agent` and `Lanes-Task` trailers by session and title (a task id from `/v1/task` is looked up on the server and mapped to that title and session; the commits carry no id), and with one task left (or one selected) builds a **new** branch `lanes/pr/<title>` at the default branch plus one commit with that task's combined changes, in a scratch worktree, so the user's checkout, index and branches are not touched. The commit is authored by the current git identity and ends with one `Co-authored-by` per other contributor: the authors of the checkpoint commits (the humans whose agents made them) and the co-authors the checkpoints name (the agent), deduplicated by e-mail, case-insensitively. Nothing is rewritten or deleted: an existing branch name is refused (no force), and the checkpoints stay on `lanes/main`. The squash commit runs the repository's own commit hooks, like every other Lanes commit (no `--no-verify`, [ADR-0023](../decisions/0023-security-baseline.md), #211). If a hook rejects it, `lanes pr` exits 1 printing the hook's output, keeps the scratch worktree with the task's changes staged on the new branch (the message is saved in the worktree's git directory) and prints `git -C <worktree> commit -F <message file>` (plus `--no-verify` for a user who decides to skip), the push command and the worktree removal command; a hook that fails because the scratch worktree has no `node_modules` says so and suggests installing dependencies there. Nothing in the user's checkout, index or other branches is touched either way. With `gh` on `PATH` and an `origin`, it pushes the branch and runs `gh pr create`; otherwise it prints the exact `git push -u origin <branch>` and says to open the PR; without a remote the branch stays local. shortcut: a task whose commits depend on another task's or an unmerged human commit does not apply alone and the command stops with the conflict; a task already squash-merged is listed again (no patch-id match).

## 2. Other agents (post-MVP)
